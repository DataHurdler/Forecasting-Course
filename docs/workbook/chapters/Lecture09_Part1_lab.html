9.1 What we are doing

Labs 7 and 8 gave you two models that could not properly use a window. The feedforward network flattened it and lost the ordering; the CNN kept ordering but could only see seven weeks at a time.

A recurrent network has neither limit. It reads the sequence in order and carries a hidden state, so in principle nothing stops it using the whole window.

Today you build two of them — a plain RNN and an LSTM — and find that at the training budget anyone would have used, the more sophisticated one loses badly. Then you vary the budget and the result changes. Working out which claim the evidence actually supports, and why, is the point of the lab, and it is the most transferable thing in it.

Time: ~40 minutes · You will need: pandas, numpy, matplotlib, torch, and data/processed/m5_weekly.csv. Most fits are quick — about six seconds each. The exception is Step 4, which trains four models to 100 epochs and takes two to three minutes; start it and read the text underneath while it runs.

9.2 Setup

import pandas as pd
import numpy as np
import matplotlib.pyplot as plt
import torch
import torch.nn as nn
import warnings
warnings.filterwarnings('ignore')

from pathlib import Path

def data_path(name):
    for base in (Path.cwd(), *Path.cwd().parents):
        p = base / "data" / "processed" / name
        if p.exists():
            return p
    raise FileNotFoundError(
        f"Could not find data/processed/{name}. "
        "Run `python scripts/prep_m5.py` from the repository root first.")

weekly = (pd.read_csv(data_path("m5_weekly.csv"), parse_dates=["week_start"])
            .sort_values(["store_id", "cat_id", "week_start"]))
CHANNELS = ["units", "snap_days", "event_days", "avg_price"]
CUTOFF   = np.datetime64("2015-05-17")
rmse = lambda a, b: float(np.sqrt(np.mean((np.asarray(a) - np.asarray(b)) ** 2)))

def build(W):
    X, Y, D = [], [], []
    for _, g in weekly.groupby(["store_id", "cat_id"]):
        arr, dates = g[CHANNELS].values.astype("float32"), g.week_start.values
        for i in range(len(g) - W):
            X.append(arr[i:i+W]); Y.append(arr[i+W, 0]); D.append(dates[i+W])
    X = np.stack(X); Y = np.array(Y, dtype="float32"); D = np.array(D)
    tr, te = D < CUTOFF, D >= CUTOFF
    mu, sd = X[tr].mean((0,1), keepdims=True), X[tr].std((0,1), keepdims=True) + 1e-8
    ym, ys = Y[tr].mean(), Y[tr].std()
    Xn, Yn = (X - mu)/sd, (Y - ym)/ys
    # recurrent layers want (batch, time, channels) -- NOT the Conv1d layout
    return (torch.tensor(Xn[tr]), torch.tensor(Yn[tr]), torch.tensor(Xn[te]), Y[te], ym, ys)

DATA = {W: build(W) for W in (13, 26, 52)}
print("shape at W=26:", DATA[26][0].shape, "(batch, time, channels)")

Neither library will complain. Both will train on nonsense.

9.3 Step 1 — A plain RNN

One recurrent layer, then a linear layer on the final hidden state — the summary after reading the whole window.

class Recurrent(nn.Module):
    def __init__(self, kind, n_channels=4, hidden=64):
        super().__init__()
        layer = nn.RNN if kind == "rnn" else nn.LSTM
        self.rnn = layer(n_channels, hidden, batch_first=True)
        self.fc  = nn.Linear(hidden, 1)
    def forward(self, x):
        out, _ = self.rnn(x)          # nn.LSTM returns out, (h, c) -- the _ absorbs both
        return self.fc(out[:, -1, :]).squeeze(-1)

def train(kind, W, seed, epochs=30):
    Xtr, Ytr, Xte, Yte, ym, ys = DATA[W]
    torch.manual_seed(seed)
    model = Recurrent(kind)
    opt = torch.optim.Adam(model.parameters(), lr=1e-3, weight_decay=1e-4)
    lossfn = nn.MSELoss()
    loader = torch.utils.data.DataLoader(
        torch.utils.data.TensorDataset(Xtr, Ytr), batch_size=128, shuffle=False)
    for _ in range(epochs):
        model.train()
        for xb, yb in loader:
            opt.zero_grad()
            lossfn(model(xb), yb).backward()
            torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)   # see below
            opt.step()
    model.eval()
    with torch.no_grad():
        score = rmse(Yte, model(Xte).numpy() * ys + ym)
    return score, sum(p.numel() for p in model.parameters())

score, n_par = train("rnn", 26, seed=1)
print(f"vanilla RNN — {n_par:,} parameters, test RMSE {score:,.0f}")

clip_grad_norm_ is not decoration. Backpropagating through 26 steps multiplies gradients repeatedly, and the product can explode. Clipping caps the update size. It is one line, it costs nothing, and recurrent models are the place you need it.

9.5 Step 3 — Which wins, and does it hold?

One comparison at one window is not evidence. Vary the window and use two seeds.

9.6 Step 4 — Was that a fair fight?

Step 3 compared two models at one training budget. Lab 7 taught you not to trust a comparison run at one seed; this is the same objection one level up. An LSTM has four times the parameters, and bigger models generally take longer to converge.

So train both to 100 epochs, and record the test RMSE along the way instead of only at the end.

CKPT = [10, 20, 30, 45, 60, 80, 100]

def curve(kind, W, seed):
    """Train once to 100 epochs, scoring the test set at each checkpoint."""
    Xtr, Ytr, Xte, Yte, ym, ys = DATA[W]
    torch.manual_seed(seed)
    model = Recurrent(kind)
    opt = torch.optim.Adam(model.parameters(), lr=1e-3, weight_decay=1e-4)
    lossfn = nn.MSELoss()
    loader = torch.utils.data.DataLoader(
        torch.utils.data.TensorDataset(Xtr, Ytr), batch_size=128, shuffle=False)
    out = {}
    for ep in range(1, max(CKPT) + 1):
        model.train()
        for xb, yb in loader:
            opt.zero_grad(); lossfn(model(xb), yb).backward()
            torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0); opt.step()
        if ep in CKPT:
            model.eval()
            with torch.no_grad():
                out[ep] = rmse(Yte, model(Xte).numpy() * ys + ym)
    return out

paths = {}
for kind in ("rnn", "lstm"):
    runs = [curve(kind, 26, s) for s in (1, 2)]        # fit each seed ONCE
    paths[kind] = [np.mean([r[e] for r in runs]) for e in CKPT]

table = pd.DataFrame({"epochs": CKPT,
                      "RNN":  [round(v) for v in paths["rnn"]],
                      "LSTM": [round(v) for v in paths["lstm"]]})
table["gap"] = table.LSTM - table.RNN
print(table.to_string(index=False))
fig, ax = plt.subplots(figsize=(6.5, 3.4))
ax.plot(CKPT, paths["rnn"],  marker="o", label="vanilla RNN")
ax.plot(CKPT, paths["lstm"], marker="o", label="LSTM")
ax.axvline(30, ls="--", lw=1, color="grey")
ax.set_xlabel("epochs"); ax.set_ylabel("test RMSE"); ax.legend()
ax.set_title("Step 3 measured at the dashed line", fontsize=9)
plt.tight_layout()
The gap is largest at exactly the budget we used

Read the gap column downwards. It is negative at 10 epochs — the LSTM is ahead early — then peaks at 30, the setting Step 3 used, and shrinks at every checkpoint after until the two models are level.

Look at the shapes, not just the endpoint. The RNN is finished by about epoch 45 and flat thereafter. The LSTM is still improving at 100 epochs; its curve has not turned over. We ran out of patience, not the model.

So the honest verdict is not “the LSTM loses.” It is:

  • at a fixed 30-epoch budget the RNN is far ahead — and 30 epochs is the point of its maximum advantage anywhere in this range;
  • given enough epochs the two are tied;
  • the RNN reaches its best score about three times faster, on a quarter of the parameters.

That last line is a real advantage and worth having. It is simply a different claim from the one the Step 3 table appears to make — and you could not have told the two apart without varying the budget.

9.7 Step 5 — Why the gates buy nothing here

The LSTM’s gates exist to solve one problem: in a plain RNN, gradients shrink as they propagate backward, so signal from far in the past never reaches the weights. Put a number on it.

for factor in (0.7, 0.9):
    print(f"gradient shrink factor {factor} per step:")
    for steps in (1, 5, 10, 26, 52):
        print(f"   {steps:>3} steps back -> {factor**steps:,.6f}")
    print()

At 0.7 per step the signal is essentially gone by 26 steps. That is the problem gating fixes.

Two things about that table before we go on. At a shrink factor of 0.7 the signal is gone by 26 steps. At 0.9 it is still 0.065 at 26 steps and 0.004 at 52 — small, but not zero. Vanishing gradients are a matter of degree and of sequence length, and 26 weeks is short.

Now stop asserting and go measure whether this dataset has the problem gating solves. Three questions, three numbers.

w = weekly.assign(series=weekly.store_id + "_" + weekly.cat_id)
w["level"] = w.groupby("series").units.transform("mean")
w["dev"]   = w.units - w.level

grand = w.units.mean()
btw = ((w.level - grand) ** 2).sum() / ((w.units - grand) ** 2).sum()
print(f"1. between-series share of total variance : {btw:.1%}")

print("\n2. within-series autocorrelation of units")
for lag in (1, 4, 13, 26, 52):
    a = w.groupby("series").dev.apply(lambda x: x.autocorr(lag)).mean()
    print(f"      lag {lag:>2}: {a:+.3f}")

print("\n3. does a flag at t predict units at t+k?")
for ch in ("snap_days", "event_days"):
    cells = []
    for k in (0, 1, 2, 4):
        c = w.groupby("series").apply(lambda g: g[ch].corr(g.dev.shift(-k))).mean()
        cells.append(f"t+{k}: {c:+.3f}")
    print(f"      {ch:<11} " + "   ".join(cells))
Three reasons the gates have nothing to do

1. Most of the variance is not sequential at all. About 91% of the variation in weekly units is between series — which store, which category — and only 9% is within a series over time. The single biggest thing a model must get right is the level of the series in front of it, and that is readable from the most recent few weeks. No memory mechanism is needed for it.

2. The series are smooth, which is the opposite of needing memory. Within-series autocorrelation is 0.83 at lag 1 and still 0.43 at lag 52. That looks like long memory and is in fact the reason long memory is unnecessary: because neighbouring weeks are nearly the same number, the recent past is a sufficient statistic for the distant past. Nothing has to be carried across the gap, because the gap has been filled in continuously along the way. Gating pays off when a value must survive many steps that would otherwise overwrite it — and here nothing overwrites anything.

3. Nothing in the inputs arrives early. snap_days correlates +0.14 with units in the same week and essentially zero at every lead; event_days is flat at every horizon including zero. There is no announcement structure in this data — nothing shows up at time \(t\) that must be stored until \(t+k\). That is the canonical use for a forget gate and an input gate, and this panel does not contain one instance of it.

So the gates solve something real, on data that does not have it. They charge four times the parameters and — as Step 4 showed — roughly three times the epochs for the service, and at convergence they return a tie.

The transferable part is the three questions, not the answer. Before reaching for a gated or attention-based model on your own series, ask: how much of my variance is cross-sectional rather than sequential? Is my series smooth enough that recent values already summarise old ones? Does anything in my inputs lead the target? If the answers look like this panel’s, the extra machinery has nothing to do.
